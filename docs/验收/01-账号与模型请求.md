## 1. 注册 → 登录 → 建 API key

### 1.1 注册（走网页，最接近真实用户路径）

浏览器打开 `$WEB/register`（生产是 `$BASE/register`）：

1. 填邮箱、用户名、密码（**至少 8 位**），点「发送验证码」。
2. **对**：跳到 `/register?step=confirm&email=…`，页面上有「验证码已发往 …，10 分钟内有效」。
3. **错**：
   - 页面报错「验证码发送失败」→ 邮件通道坏了（生产 `app.yml` 的 mailer 是 `transport: log`，
     验证码只在**日志**里；换成 `smtp` 才有真邮件）
   - 停在 `/register` 没跳 → 密码强度不够或邮箱非法
4. **本地开发拿验证码**：看 dizzyapi 的日志，搜 `[log 投递] to=<你的邮箱>`，
   下一行就是 6 位数字（`packages/mailer/src/index.ts` 的 log 投递分支）。
5. 填验证码 → 点「完成注册」。
   - **对**：跳到 `/console/usage`，**已经登录**（注册即登录，不用再登一次）。
   - **错**：仍停在 `/register` → 验证码错/过期（10 分钟）/ 已被用过。

> 首个注册用户**自动成为管理员**；之后注册的都是普通用户（要测越权就多注册一个）。

### 1.2 登录（已有账号）

浏览器 `$WEB/login`，邮箱 + 密码 → 「登录」。

- **对**：跳到 `/console/usage`，左侧有侧栏（用量信息 / 模型广场 / API 文档 / API keys / 充值 / 兑换 / 账单 / 个人资料）。
- **错**：
  - 页面报「邮箱或密码不正确」→ 凭据错
  - 报「登录尝试过于频繁」→ 15 分钟内失败 10 次（`loginMaxFailures: 10`），等 15 分钟
  - 报「当前账号不可用」→ 账号被封禁（403 `AUTH_USER_BANNED`）

### 1.3 建 API key（网页）

浏览器 `$WEB/console/api-keys`：

1. 填名称 → 「创建」。
2. **对**：出现一块**只显示一次**的完整 key（形如 `sk-…`），上面有绿色提示
   「新的 API key 已生成，只显示这一次，请立即保存。」**立刻复制走**。
3. **错**：
   - 没出现完整 key → 页面报错「API key 服务未运行」
   - 刷新后完整 key 消失 → **这是对的**（一次性显示，库里只存哈希 + 掩码）；
     真要再看只能轮换（`/console/api-keys` 每行的「轮换」）。

> ⚠️ 完整 key **只在创建 / 轮换的那一次响应里出现**。它不进日志、不进 URL、不进 localStorage。
> 忘了存就轮换一把。

### 1.4 建 API key（API 面，可脚本化）

```bash
export SESSION="dizzyapi_session=<从浏览器 DevTools → Application → Cookies 复制>"
curl -sS -X POST "$API/api/keys" \
  -H "Cookie: $SESSION" -H "X-Requested-With: dizzyapi" \
  -H "Content-Type: application/json" \
  -d '{"name":"验收用"}'
```

- **对**：200，`{"id":"…","secret":"sk-…","maskedKey":"sk-…abcd", …}`
- **错**：
  - `401 API_UNAUTHORIZED` → 没带会话或会话过期
  - `403 API_REQUEST_HEADER_REQUIRED` → 少 `X-Requested-With`
  - `409 API_KEY_LIMIT_REACHED` → 该用户 key 数达上限（默认 100）
  - `503 API_KEY_UNAVAILABLE` → api-key 插件不在运行

**出处**：`packages/api/src/routes/auth.ts`（register/request、register/confirm、login）、
`packages/api/src/routes/keys.ts`（`POST /api/keys`）。

## 2. `/v1/chat/completions` 发一条真请求

```bash
export KEY="sk-刚才复制的那把"

curl -sS -i "$LLM/v1/chat/completions" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<对外模型名>","messages":[{"role":"user","content":"说一句话"}]}'
```

> 「对外模型名」从 `$LLM/v1/models` 取（见 §2.1）。**填错模型名会被路由层拒**（见 §2.3）。

### 2.1 先看可用模型

```bash
curl -sS "$LLM/v1/models" -H "Authorization: Bearer $KEY"
```

- **对**：200，`{"object":"list","data":[{"id":"<模型名>",…}]}`
- **错**：
  - `401 INVALID_API_KEY` → key 不对，或**网关还没收到 key 快照**（见 [06-上线顺序.md](06-上线顺序.md)）
  - `{"data":[]}` → 账号池里没有账号声明任何模型（上游没配好）

### 2.2 正常请求的判据

- **对**：
  - HTTP `200`
  - 响应体是 OpenAI 形状：`{"id":"…","object":"chat.completion","choices":[{"message":{"role":"assistant","content":"…"}}],"usage":{…}}`
  - **响应头有 `X-Request-Id`**（这是后面查用量的唯一凭据，务必记下来）
- **错**：
  - `401 INVALID_API_KEY` / `401 MISSING_API_KEY` → 鉴权没过（key 错 / 没带 `Bearer`）
  - `403 MODEL_NOT_PRICED` → 定价闸门开着而这个模型没配价（[05-管理台与内容审核.md](05-管理台与内容审核.md) §8.3）
  - `402 INSUFFICIENT_BALANCE` → 余额不足（[03-额度闸门与协议入口.md](03-额度闸门与协议入口.md) §4）
  - `402 API_KEY_SPENDING_LIMIT` → 这把 key 的金额上限到了
  - `429 API_KEY_CONCURRENCY_LIMIT` / `429 USER_CONCURRENCY_LIMIT` → 并发满（[05-管理台与内容审核.md](05-管理台与内容审核.md) §8.5）
  - `503 ALL_ACCOUNTS_SATURATED` → 所有候选账号都在冷却 / 都被占满
  - `503 NO_ELIGIBLE_ACCOUNT` → 没有任何账号能服务这个模型
  - `503 QUOTA_SNAPSHOT_UNAVAILABLE` → 严格模式下余额快照不可用
  - `404 MODEL_NOT_SERVED` → 账号池里没有账号声明这个模型
  - `400 INVALID_REQUEST` → 请求体不是合法 JSON，或缺 `model`
  - `405 METHOD_NOT_ALLOWED` → 用了 GET（这些入口只收 POST）

> **错误体形状按协议变**（`contracts/protocol.go` 的 `RenderError`）：
> - OpenAI 系（`/v1/chat/completions`、`/v1/responses`）：`{"error":{"message","type","code"}}`
> - Anthropic（`/v1/messages`）：`{"type":"error","error":{"type","message","code"}}`（`code` 是**纯增量**字段）
> - Gemini（`/v1beta/…`）：`{"error":{"code":<整数状态>,"message","status","reason"}}`
>   （`code` 是**整数**，网关的稳定码放在 `reason` 里）
>
> `type` 的映射：401/403 → `authentication_error` / `permission_error`，
> 429 → `rate_limit_error`，5xx → `server_error`，其余 → `invalid_request_error`。

### 2.3 模型名不对的样子

```bash
curl -sS -o /dev/null -w '%{http_code}\n' "$LLM/v1/chat/completions" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"不存在的模型","messages":[{"role":"user","content":"x"}]}'
```

- **对**：`404`，`error.code = MODEL_NOT_SERVED`（**不转发上游**，不花钱）
- **错**：200（说明路由没按 `models` 过滤，是回归）

### 2.4 流式请求（顺便验 SSE 与 TTFT）

```bash
curl -sS -N "$LLM/v1/chat/completions" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"<对外模型名>","messages":[{"role":"user","content":"数到十"}],"stream":true}'
```

- **对**：`data: {...}` 一帧一帧出来，最后一帧是 `data: [DONE]`
- **错**：一次性吐完整 JSON（说明流式没走通）

> 流式请求才会采集 **TTFT（首字延迟）**，非流式请求的 TTFT 永远是「未采集」。
> 用量页里非流式记录显示「—」是**对的**，不是 bug。

**出处**：`internal/httpapi/server.go`（`mux.HandleFunc` 与 `llmHandler`）、
`contracts/protocol.go`（`RenderError`）、`modules/keyauth/module.go`（`INVALID_API_KEY`）。
