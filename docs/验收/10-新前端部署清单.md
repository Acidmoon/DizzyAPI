## 1. 构建产物：两条路线，推荐「本地 build + scp 产物」

### 1.1 先看产物是什么

`packages/dashboard/app/next.config.mjs`（**已合进 `main`，不是草稿**）：

| 配置 | 值 | 含义 |
|---|---|---|
| `output` | `"export"` | **纯静态导出**，没有 Node 运行时、没有 SSR |
| `trailingSlash` | `true` | 每条路由产出 `<route>/index.html`，插件回退规则简单 |
| `images.unoptimized` | `true` | 静态导出没有图片优化服务 |
| `reactCompiler` | `true` | |
| `compiler.removeConsole` | 生产构建去掉 `console.*` | |
| CSP nonce | **不在 Next 里做** | 静态导出没有 middleware，nonce 由插件返回 HTML 时改写字节注入（`src/csp.ts`） |

- 依赖规模：`dependencies` 35 个 + `devDependencies` 15 个，`next@^16.4.3`。
- 这个 app **有自己的 `package-lock.json`**（npm），**不是**根 pnpm workspace 的一部分
  —— 它要在自己的目录里单独 `npm ci`。
- 上游带过来的 `deploy` 脚本（`opennextjs-cloudflare`）与 `vercel.json` 都已删。
- **产物是什么样**（`main` = `eb24bbb` 实测）：**20 个页面路由**
  （管理台 13 + 用户 4 + 落地 / 登录 / 注册 3）。文件数与体积**以实际构建日志为准**
  —— 上次完整构建是 17 路由时的 **134 个文件 / 3.98 MiB**，路由还在按批次增长。

### 1.2 产物目录：**已定，插件读 `packages/dashboard/dist`**（第一版的疑点已销账）

第一版担心「注释说 `dist/` 但 Next 默认是 `out/`」。**这个矛盾已经用一步构建脚本消掉了**：

```text
next build  →  packages/dashboard/app/out/        （Next 的固定产物目录）
     ↓  node scripts/export-dist.mjs  （build 脚本的后半段，自动执行）
packages/dashboard/dist/                          （插件读这个）
```

三处证据，都在 `main` 上：

| 证据 | 内容 |
|---|---|
| `packages/dashboard/app/scripts/export-dist.mjs` | 把 `out/` 拷成 `../dist`；顺带写 `dist/build-info.json`（§1.6） |
| `packages/dashboard/src/paths.ts` 的 `defaultDistDir()` | `new URL('../dist', import.meta.url)` → 解析成 `packages/dashboard/dist`（**按包位置算，不靠 `process.cwd()`** —— 生产进程 cwd 是 `/opt/dizzyapi`，靠 cwd 拼会拼错） |
| `packages/dashboard/src/config.ts` 的 `DASHBOARD_DEFAULTS` | `{ port: 7792, enabled: true }`；`distDir` 不配就用 `defaultDistDir()` |

**配置项名（第一版的待确认 #4）**：`distDir`（`config.ts:24` / `:45`，`writable: false`）。
生产**不用配**（默认值就是对的），只有产物放在别处时才需要。
**注意它是只读字段**：改它要重启，不会软生效。

### 1.3 两条路线

| | **A. 本地 build，scp 产物**（推荐） | B. 服务器上 build |
|---|---|---|
| 做法 | 本地 `pnpm build:dashboard`（= `npm --prefix packages/dashboard/app run build`）→ 把 `packages/dashboard/dist/` 整体 scp 到服务器 | 服务器上 `npm ci && npm run build` |
| 服务器需要 | 只要 Node（已在跑）+ 目标目录 | Node **+ 能装 523 个 npm 包** |
| 增量 | 只传变了的产物 | 源码变了就重装 + 重建 |
| 主要风险 | 本地产物与服务器 Node 版本差异（纯静态，风险低） | **`AGENTS.md` §6.3 已记录：服务器上 `pnpm` 走网络会卡**；npm 同理，且服务器没有 Go 工具链的先例说明「服务器只跑，不构建」是既定风格 |
| 可复现性 | 产物不可复现（没有 lockfile 之外的保证），但**能被 `git archive` 的源码复现** | 好一点，但踩网络 |

**推荐 A**，理由是仓库现有的部署风格就是「本地交叉编译 → scp 二进制」：
`bin/gatewayd` 从来不在服务器上编（`AGENTS.md` §6.3）。前端产物照同一模式处理，
运维心智只有一条：「服务器只跑构建好的东西」。

### 1.4 A 方案的具体步骤

```bash
# ── 本地：装依赖 + 构建（app 有自己的 package-lock.json，走 npm 不走 pnpm）
#    根 package.json 已经有现成脚本：pnpm build:dashboard
#      = npm --prefix packages/dashboard/app run build
#      = next build && node scripts/export-dist.mjs     ← 后半段把 out/ 拷成 dist/ 并写构建戳
npm --prefix packages/dashboard/app ci       # 首次或依赖变了才需要
pnpm build:dashboard                          # 在仓库根执行

# ── 本地：先自查构建戳（§1.6，别等到服务器上才发现 dirty）
cat packages/dashboard/dist/build-info.json

# ── 本地：代码（排除服务器上才对的配置）
git archive --format=tar HEAD -- . ':!app.yml' ':!cordis.yml' \
  | ssh root@<SERVER_IP> 'cd /opt/dizzyapi && tar xf -'

# ── 本地：产物（**不在 git 里，git archive 不会带**；目录是 dist/，不是 app/out/）
tar -C packages/dashboard -cf - dist \
  | ssh root@<SERVER_IP> 'cd /opt/dizzyapi/packages/dashboard && tar xf -'
```

三条纪律（都来自 `06-上线顺序.md` §10.3，这里只复述与本部件相关的部分）：

1. **`app.yml` 与 `cordis.yml` 必须排除** —— 服务器那份才对（`account-priority.httpListen: 18080`、
   `mailer.from`）。
2. **产物必须单独传**：`git archive` 只带被跟踪的文件，`packages/dashboard/dist` 被根 `.gitignore`
   明确忽略（那条规则就写在 `.gitignore` 末尾：`/packages/dashboard/dist`），**不会**跟源码一起过去。
   漏了就是「插件起来了、页面 404」。
3. **`data/`、`bin/` 不在 git 里**，天然不会被覆盖；`bin/gatewayd` 按 `06-上线顺序.md` 单独换。

### 1.5 服务器上的目录与权限

- 代码根：`/opt/dizzyapi`；systemd：`dizzyapi.service`。
- 产物落到 **`/opt/dizzyapi/packages/dashboard/dist/`**（与仓库里的相对位置一致；
  插件按**包自身位置**解析，不靠 `process.cwd()`，所以必须放在这个位置）。
- **产物目录不要在 `data/` 下**：`data/` 是「不能被部署覆盖」的目录，产物是「每次部署都要换」的，
  混在一起会让人不敢覆盖、也不敢清理。
- **回滚要用的上一份产物**：按 `packages/dashboard/README.md` 的部署口径保留成 `dist.prev`
  （改名 + 重启，不用重新 build，见 §4）。

### 1.6 构建戳 `dist/build-info.json`：**scp 完先核它，再重启**

`export-dist.mjs` 每次构建都会写一份（下面是**形状示例**，值以实际构建为准；
`总工` 在 `main` 的干净工作区实测过一次：`dirty:false`、`files:134`）：

```json
{ "commit": "<构建时的 HEAD 短 hash>", "dirty": false, "builtAt": "2026-10-31T03:41:45.970Z", "files": 134, "bytes": 4174311 }
```

- `commit` = `git rev-parse --short HEAD`；`dirty` = 工作区有没有未提交改动；
  `files` / `bytes` = **导出内容本身**（不含 `build-info.json` 自己）。
- git 不可用时落 `commit: "unknown"` / `dirty: null`，**不让构建崩**。

**为什么必须有这一步**：`dist/` 是 gitignored 的构建产物，插件读的是**磁盘上当前那一份**，
**它不认 git commit**。所以「代码已经合进 main、但服务器上的 dist/ 还是上一版」在服务器上是
**完全静默**的 —— 页面照常 200，只是内容是旧的。构建戳是唯一的识别手段。

**验收动作（必做，先于重启）**：

```bash
# ① 服务器上直接读文件（最可靠，不依赖服务已起来）
ssh root@<SERVER_IP> 'cat /opt/dizzyapi/packages/dashboard/dist/build-info.json'

# ② 或者等插件起来后从公网读（它是 dist/ 根的普通静态文件，
#    插件按 .json → application/json + no-store 发，不会读到旧缓存）
curl -sS https://<站点域名>/build-info.json
```

**判据（两条都要满足，缺一条就停下）**：
1. `commit` **等于要发的那个 main commit**（同一个短 hash）；
2. **`dirty` 必须是 `false`**。

> ⚠️ **`dirty: true` 的产物不许上服务器。** 那种产物「到底发的是哪个 commit」没有答案
> —— `commit` 只记 HEAD，工作区里那些未提交改动不在任何 commit 里。`export-dist.mjs` 自己会在
> `dirty: true` 时往构建日志打一行警告（`警告：工作区有未提交改动，这份产物不许上服务器。`），
> 但**它不会让构建失败**（刻意如此：构建产物不该因为 git 状态而建不出来），所以**必须人去看**。
> 本地自查的那一步（§1.4 的 `cat ../dist/build-info.json`）就是为了在出发前挡住它。

## 2. nginx：**端口不用改，但 `/api/*` 的 `Origin` 改写必须核**（这是第二版新发现的真风险）

现状（出处：`docs/验收/06-上线顺序.md` §10.3 与 `AGENTS.md` §6.3，**我未在服务器上核实**）：

| 路径 | 反代到 | 改写 |
|---|---|---|
| `/v1/*`、`/v1beta/*`、`/healthz` | gatewayd `127.0.0.1:18080` | — |
| `/api/*` | `api` 插件 `127.0.0.1:7791` | `Host` → `127.0.0.1:7791`；**`Origin` → `http://127.0.0.1:7791`（要核，见下）** |
| 其余（含 `/`） | 前端插件 `127.0.0.1:7792` | `Host` → `127.0.0.1:7792`；`/` 还要 `Origin` → `https://127.0.0.1:7792` |

**结论：监听 7792 这一点不变，所以端口/落点不用改。但 `Origin` 这条要重新看。**

⚠️ 三个前提：

1. **`web` 必须先停**，否则 `EADDRINUSE`（`packages/web/src/config.ts` 明写「端口冲突直接失败，
   不静默换端口」；新插件 `static-server.ts:74` 同一口径）。顺序见 §3。
2. **`Host` 校验已经做了**（第一版的待确认 #3 **已销账**）：
   `packages/dashboard/src/static-server.ts:270-276` 的 `hostAllowed()` 只认
   `127.0.0.1:<port>` / `localhost:<port>`，外加配置里的 `extraAllowedHosts`；
   不匹配回 **421 Misdirected Request**。与 `web`/`api` 同一口径，nginx 的 `Host` 改写值不变。
3. **`/api/*` 的 `Origin` 改写：这是切换新 SPA 才暴露出来的新依赖**（详见 09 册 §3.2）：
   - 旧前端的所有写操作是**表单 POST 打 7792**，`web` 的 `assertSameOrigin` **比 host 不比协议**，
     所以 nginx 把 `Origin` 改写成 `https://127.0.0.1:7792` 就能过。
   - 新前端**所有写操作走 `/api/*`（7791）**，`api` 的 `assertOrigin`
     （`packages/api/src/http.ts:201-213`）是**精确字符串比对**
     `['http://127.0.0.1:<port>', 'http://localhost:<port>']` —— 是 **`http://`**。
   - 浏览器**同源的 POST / PATCH / DELETE 也会带 `Origin`**（GET / HEAD 不带）。
     所以新 SPA 发 `PATCH /api/keys/<id>` 时带的 `Origin: https://<站点域名>`，
     若 nginx 原样转发 → **403 `API_ORIGIN_FORBIDDEN`**。
   - **注意「已经改写过 Origin」也不够**：如果服务器的 nginx 是在 server 块里统一把 `Origin`
     改写成 `https://127.0.0.1:7792`（就是为 `/` 配的那条），那 `/api/*` 拿到的会是
     **7792 的 Origin**，而 `api` 插件要的是 **`http://127.0.0.1:7791`** —— 照样 403。
     值要**按 location 分别写**，不是一个全局值能同时满足两处。
   - 既有记录里**只写了 `/` 要改 `Origin`**，`api` 的 `/api/*` 那条从来没被触发过（旧前端不这么发请求）。
   - **`命令行` 线的 11 册独立发现了同一条**（[11-cli-api-依赖清单.md](11-cli-api-依赖清单.md) 第 2 条，
     原文「这是给 `工具` / 部署线的」）—— 两条线各自推出来同一个结论，说明这不是孤例。
   - **要么** nginx 的 `/api/*` location 加 `proxy_set_header Origin http://127.0.0.1:7791;`，
     **要么** 改 `api` 插件接受真实 Origin（要动代码，属另一批）。
     建议前者：一行配置，不改代码。
   - **症状识别**：页面能打开、能读，**一改东西就 403** 且错误码是 `API_ORIGIN_FORBIDDEN`
     → 就是这条没配。**不是登录问题**（登录问题是 401 `AUTH_*`）。

> 仓库里**没有 nginx 配置文件**（`*.conf` / `nginx*` 全仓零命中），宝塔那份只在服务器上。
> 所以上面这张表是「既有记录的复述」，不是我实测的。**上线前 `ssh` 上去看一眼实际配置**，
> 重点看 `/api/*` 那个 location 有没有 `proxy_set_header Origin`。

## 3. 部署顺序：**先起新、再摘旧、一次重启**（不能反过来）

### 3.1 为什么不能「先关旧的上新的」

两个插件抢 7792 会起不来；而如果先摘掉 `web` 再上新插件，中间那段时间 7792 没有监听
→ nginx 502 → **整站（除 `/api/*`、`/v1/*`）全部 502**。窗口可能只有几秒，但没必要。

### 3.2 正确顺序

```text
① （上一批已做）代码里已经有 packages/dashboard 且 npm 产物已 scp 到位
② 改 app.yml：**只加** dashboard 条目，先别删 web 条目
   但此时两者都配 7792 → 会抢端口
```

**这里有矛盾，必须解决。** 三个可选做法：

| 做法 | 步骤 | 评价 |
|---|---|---|
| **① 换端口过渡**（推荐） | 新插件先配 `port: 7793`（`deepseek-usage` 已禁用，端口空着）→ 起来后用 `curl 127.0.0.1:7793` 验活 → 改 `app.yml`：删 `web` 条目、把 dashboard 改回 `7792` → **一次**重启 → nginx 无感 | 多一次重启，但**零 502**：7792 在切换那一刻由「旧 web」直接变成「新 dashboard」 |
| ② 一次改完再重启 | 同一个提交里「删 web + 加 dashboard(7792)」→ 重启 | 最快，但**新前端第一次上生产就等于「直接替换」**，没有中间验活的机会；出问题只能回滚 |
| ③ 反向代理指到新端口 | 改 nginx 指向 7793，插件随便起 | **要动 nginx**，而且 `Host` 改写值也得跟着改 → 违反「nginx 不用改」的前提 |
| ④ 先停 `web` 再起新 | `disabled: true` 掉 web → 重启 → 加 dashboard → 再重启 | 中间有 502 窗口，不推荐 |

**推荐 ①**：用 `7793` 当过渡端口（它现在是 `deepseek-usage` 的，而那个插件 `app.yml:328` 已 `disabled: true`，
端口空着）。这样「新前端能不能起来、`/` 与 `/auth/v2/login/` 通不通」可以在**不影响线上**的情况下先验一遍，
最后一步只是「把 7792 这个名字从旧插件换给新插件」，重启一次。

### 3.3 完整步骤（按推荐 ①）

```text
0. 备份：/opt/dizzyapi/data/ + /opt/dizzyapi/app.yml（cp 成 app.yml.bak-YYYYMMDD）；
   dist/ 若已存在先改名 dist.prev（回滚用，§4-③）
1. 传代码（git archive，排除 app.yml / cordis.yml）+ 传前端产物 packages/dashboard/dist（§1.4）
2. **先核构建戳**（§1.6）：cat /opt/dizzyapi/packages/dashboard/dist/build-info.json
   → commit == 要发的 main commit 且 dirty == false，否则**停在这里，不要重启**
3. 改服务器 app.yml：新增 dashboard 条目（port: 7793 作过渡）；**web 条目原样留着**
4. 重启 → 验：systemctl is-active / 本机 curl 7793
   curl -sS -H 'Host: 127.0.0.1:7793' -o /dev/null -w '%{http_code}' http://127.0.0.1:7793/
   curl -sS -H 'Host: 127.0.0.1:7793' http://127.0.0.1:7793/build-info.json
5. 若 4 通：改 app.yml —— 删 web 条目、dashboard 的 port 改成 7792
6. 再重启一次 → 验 §5.1 的机器可验项（尤其 **/api/* 写操作不是 403**）
7. 若 4 不通：直接回滚（§4），**服务器上什么都没坏**
```

> ⚠️ 第 3 步的 7793 只是**过渡**，不要让它活到切换之后：两个前端插件长期并存会让
> 「哪个在服务用户」变得含糊。
>
> ⚠️ **过渡期的 `Host` 要跟着端口走**：新插件的 `hostAllowed()` 认的是
> `127.0.0.1:<实际监听端口>`，配 7793 时就得用 `Host: 127.0.0.1:7793` 去 curl。
> 这一步本地验证**不需要** nginx，直接在服务器上 curl 回环。

## 4. 回滚：三条路，按「快」排

| 手段 | 怎么做 | 适用 |
|---|---|---|
| **① 只改配置**（最快，1 分钟） | `app.yml` 把 dashboard 条目 `disabled: true`、`web` 条目加回来 → 重启 | **代码没问题、只是新前端有问题**。旧插件代码还在服务器上（没删过），能直接起 |
| ② 回退代码 | `git revert` 那个「删旧前端」的提交 → `git archive` 重新传 → 重启 | 已经删了包、旧插件文件不在了 |
| ③ 回退产物 | 把上一次备份的产物目录 tar 恢复 → 重启 | 只换了前端产物、插件没动 |

**关键约束：`web` 从 `app.yml` 摘掉 ≠ 删代码。** 回滚速度取决于「旧插件代码还在不在服务器上」：

- 阶段 5 **第一批**（只加 dashboard、`web` 保持 `disabled: true`）→ 回滚就是翻一个 `disabled` 开关；
- 阶段 5 **第二批**（真删包）之前，**必须确认线上稳定观察期过了**（建议至少一次完整验收 + 24h）。
  删包之后就只剩 `git revert` 这条路，慢但可行（历史都在）。

## 6. 已知雷区（逐条都是踩过的）

1. **`bin/gatewayd` 要先换再重启** —— 顺序反了全站 401。详见 [06-上线顺序.md](06-上线顺序.md) §10.2。
   本册的前端改动**不改变**这条的顺序，别因为「只换了前端」就跳过它。
2. **`app.yml` 不能被 `git archive` 覆盖** —— 服务器那份的 `httpListen: 18080`、
   `mailer.from`、`gate-feed` 条目都是服务器专有。排除式见 §1.4。
3. **前端产物不在 git 里** —— `git archive` 带不走（根 `.gitignore` 有一条
   `/packages/dashboard/dist`），必须单独 tar/scp。漏了就是页面全 404；
   而且**症状是 503 不是 404**（`static-server.ts` 在 `index.html` 也不存在时回
   `503 静态产物不存在：先构建 packages/dashboard/dist`，刻意不假装 404）。见到这条 503，
   第一反应是「产物没传」，不是「代码坏了」。
4. **端口 7792 只能有一个主人** —— 旧 `web` 没摘掉之前，新插件不能配 7792。见 §3.2 的过渡方案。
5. **`sub2api` 在 `127.0.0.1:8080`，不要动** —— 它跟本项目共存于同一台机器。
6. **服务器上装依赖会卡** —— 这也是 §1.3 推荐「本地 build」的原因之一。
   而且 `packages/dashboard/app` 是**独立 npm 工程**（`README.md` 记的是 **523 个包**），
   那个 pnpm store 里**没有**它们。
7. **CSP 两套口径别混（这是最容易改错的一条）** ——
   旧 `web` 是**纯 `'self'`、零 inline**；新 `dashboard` 是
   `script-src 'self' 'nonce-…'` + `style-src 'self'` + **`style-src-attr 'unsafe-inline'`**
   （owner 2026-10-31 拍板「按模版来」，理由见 09 册 §8）。
   **改了 `style-src-attr` 就是改坏了**（侧栏宽度会塌、弹窗定位错、图表尺寸 0）；
   **放开 `script-src 'unsafe-inline'` 同样是改坏了**（`csp.ts` 的注释把这两条写成「不接受的做法」）。
   nonce 是**每次响应新生成**的（`newNonce()` = 16 字节 base64），不许固定成常量。
8. **回滚的观察期**（§4）：删包之后回滚要 `git revert`，比翻开关慢。删包前先观察一轮。
9. **`dirty: true` 的产物不许上服务器**（§1.6）—— 脚本只警告不失败，靠人核。
10. **`/api/*` 的 `Origin` 改写**（§2 第 3 条）—— 症状是「能看不能改，403 `API_ORIGIN_FORBIDDEN`」。
