## 6. CSV 导出（**浏览器真点**）

> 这一条是上次明确「未验证」的那条：**必须用浏览器点，不能只看 HTTP 头**。
> 目的不是验接口，是验**浏览器真的把文件存下来了**。

### 6.1 浏览器点

1. 浏览器打开 `$WEB/console/usage/detail`（明细页）。
2. 顶部有筛选下拉（时间档位 / 模型 / API key），先按 §6.2 的口径设好筛选。
3. 点「**导出 CSV**」按钮。
   - 它是**普通链接**（`<a class="btn" href="/console/usage/export.csv?…">`），
     **不需要任何脚本**——所以没 JS 也能下载（这是设计）。
4. **对**：
   - 浏览器**直接下载**一个 `.csv` 文件（不弹新页面、不显示乱码文本）
   - 文件名形如 `usage-20261030.csv`（单日）或 `usage-20261001-20261030.csv`（跨天），
     **按本地时区**
   - 用 Excel 打开：**中文不乱码**（文件头有 UTF-8 BOM），列对齐
5. **错**：
   - 页面显示一坨文本 / 下载的是 `.json` → 路由或 Content-Type 不对
   - 文件名乱码 → `Content-Disposition` 的 `filename*` 没给对
   - Excel 里中文乱码 → BOM 丢了

### 6.2 导出的内容必须与表格一致

⚠️ **先分清两个口径**：表格是 **keyset 分页，每页 20 条**；导出是**该筛选下的全部记录**
（上限 5 000 条，服务侧硬上限 20 000）。所以：

- 筛选结果 **≤ 20 条**时：导出的数据行数 **==** 表格里的行数，逐行对得上（最省事的对账方式）
- 筛选结果 **> 20 条**时：导出的数据行数 **==** 表格翻到最后一页累计的行数，
  **不是**当前这一页的行数（这是设计：导出要全量，表格是分页看的）

```bash
# 下载后的文件：表头 1 行 + N 条记录
wc -l usage-*.csv
```

- **对**：N == 该筛选下的记录总数；每行的 `time` / `model` / `api_key` 与表格逐行对得上
- **错**：N 比总数少 → 筛选没下传（导成了别的范围）；N 比总数多 → 越权或上限问题

> 想做最严的对账，就把筛选收窄到 **20 条以内**（比如只选一个模型 + 只选今天），
> 这时表格行数与导出行数必须**完全相等**。

### 6.3 表头是 12 列，**不含 `ttft_ms`**

```bash
head -1 usage-*.csv
```

- **对**：
  ```
  time,api_key,model,input_tokens,output_tokens,cache_read_tokens,cache_write_tokens,total_tokens,cost_micros,status,duration_ms,client_ip
  ```
  正好 **12 列**。`ttft_ms` **不在里面**——那是 `/api/usage/export` 的既有契约，
  单一实现必须原样沿用；`ttft_ms` 只出现在**页面表格**与**详情弹窗**里。
- **错**：多了或少了列 → 格式实现漂了

### 6.4 `client_ip` 列必须真的有值

```bash
# 挑一行，看最后一列是不是 IP
awk -F',' 'NR==2 {print $NF}' usage-*.csv
```

- **对**：是客户端 IP（形如 `203.0.113.9`）
- **错**：**永远是空的** → 表头承诺了却不给数据（比不给这列更糟）。2026-10-30 修过一次，
  现在有护栏钉着（`packages/usage/test/csv.test.ts` 与 `usage.test.ts` 两条）

### 6.5 公式注入防护

如果你在测试环境造过名字以 `=` 开头的 API key 或模型名：

```bash
grep -n "'=" usage-*.csv
```

- **对**：那些单元格前面**多了一个单引号**（`'=HYPERLINK(…)`）——
  这是防公式注入（CSV 里的 `=…` 在 Excel 打开时是活公式，不是文本）
- **错**：没有前导单引号 → 有人下载后打开就执行了

### 6.6 未登录点导出

把浏览器 cookie 清掉（或用无痕窗口）再点：

- **对**：**302** 跳到 `/login?err=请先登录`（不是 401，也不是下载一个空文件）
- **错**：401 / 下载到空 CSV / 500 → 路由层判错了

### 6.7 API 面那条 JSON 契约（**没变**，别改坏）

```bash
curl -sS "$API/api/usage/export?range=7d" \
  -H "Cookie: $SESSION" -H "X-Requested-With: dizzyapi"
```

- **对**：200，`{"filename":"usage-20261013-20261019.csv","content":"﻿time,api_key,…"}`
  —— **`filename` 是 UTC 日期且始终两段**，这是历史契约，逐字不变
- **错**：字段名变了 / `content` 里没有 BOM → 契约破了（现有用例钉着）

> 两条路都合法，别混：**网页下载**走 `web` 的 `text/csv`（普通链接、零脚本）；
> **API 取**走 `api` 的 JSON `{filename, content}`（客户端自己拼 Blob）。
> 两处出的**是同一份字节**（格式只有一份实现）。

**出处**：`packages/web/src/usage-export.ts`（路由与响应头）、
`packages/usage/src/csv.ts`（唯一格式实现）、`packages/api/src/routes/usage.ts`（`usageExport`）。

## 7. 越权回归（**必须 404，不许是空列表**）

> 这是 2026-10-30 修掉的**真漏洞**：第 3 批第一版的 `/console/usage` 两页查询**没带 `userId`**，
> 而 usage 服务缺 `userId` 时是**全站口径**（管理面语义）→ 任意登录用户能看到全站用量、
> 别人的模型名、API key 名与金额。生产当时跑的是旧版，**没被暴露**，但 main 上已修。

### 7.1 准备两个账号

- **A**：普通用户，有自己的用量记录
- **B**：另一个普通用户（或管理员），有 B 自己的记录

各建一把 API key，各发一条请求（[01-账号与模型请求.md](01-账号与模型请求.md) §2）。

### 7.2 A 的会话查 B 的记录 → 必须 404

```bash
# 先拿到 B 的 reqId（B 自己查 [02-用量与费用对账.md](02-用量与费用对账.md) §3.2 得到）
export BREQID="<B 的 X-Request-Id>"

curl -sS -i "$API/api/usage/$BREQID" \
  -H "Cookie: $A_SESSION" -H "X-Requested-With: dizzyapi"
```

- **对**：HTTP `404`，`error.code = USAGE_RECORD_NOT_FOUND`
- **错**：
  - `200` 还能看到 B 的记录 → **越权还在**，立刻停下来
  - `200` 但内容是空的 → 形状不对（这不是「查不到」的正确形状）
  - `403` → 也不对：这里**不是权限不足，是「没有这条记录」**，
    **不泄露某个 reqId 是否存在**（与充值订单「用户面不泄露存在性」同一条纪律）

### 7.3 A 的会话查 B 的 reqId **不存在** → 也是 404（同样形状）

```bash
curl -sS -i "$API/api/usage/req-does-not-exist-12345" \
  -H "Cookie: $A_SESSION" -H "X-Requested-With: dizzyapi"
```

- **对**：`404` + `USAGE_RECORD_NOT_FOUND`，**与 §7.2 的响应形状逐字相同**
- **错**：给的是 403 / 400 / 别的 code → 说明「存在性」被泄露了

### 7.4 A 的列表里不许有 B 的数据

```bash
curl -sS "$API/api/usage?range=30d" \
  -H "Cookie: $A_SESSION" -H "X-Requested-With: dizzyapi" | grep -c "<B 的 reqId>"
```

- **对**：`0`
- **错**：`≥1` → 越权

### 7.5 网页面也不许漏

浏览器用 A 的身份打开：

- `$WEB/console/usage`（概览）：指标卡、图、**最近 10 条**里都不许出现 B 的模型名 / key 名 / 金额
- `$WEB/console/usage/detail`（明细）：表格里不许出现 B 的行
- `$WEB/console/usage/detail?reqId=<B 的 reqId>`：**整页说「没有这条记录」**，
  **不是**显示 B 的详情
- `$WEB/console/usage/export.csv`：**导出的文件里不许有 B 的行**

### 7.6 管理面仍然全站可见（对照组）

用管理员会话查 B 的记录：

```bash
curl -sS -i "$API/api/usage/$BREQID" \
  -H "Cookie: $ADMIN_SESSION" -H "X-Requested-With: dizzyapi"
```

- **对**：`200`，能看到 B 的记录
- **错**：404 → 管理面被误伤（`roleOf(view.user) === 'admin'` 的分支坏了）

**出处**：`packages/api/src/routes/usage.ts`（`usageDetail` 里
`row.userId !== view.userId` → 404）、`packages/web/src/usage-view.ts`
（`queryOf(filters, userId)` 的 `userId` 是**必填位**）、
`packages/web/test/pages-usage.test.ts`（「越权回归」两条双向护栏）。
